# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Documentation and automation repository for an industrial automation and energy management development lab. The lab has three physical subsystems: **Development** (MOD-1, NS-1, PC-1), **Energy Management Assembly** (MOD-2, NS-2, PC-2, AP-2), and **Target Hardware** (RTAC-1, MET-1, DEV-1).

## Key Commands

```bash
# Propagate network.json changes to all device docs and README registry
python3 scripts/sync-device-docs.py

# Preview changes without writing files
python3 scripts/sync-device-docs.py --dry-run

# Check for inconsistencies (stale tags, missing markers, IP conflicts, broken links)
python3 scripts/sync-device-docs.py --validate
```

## Source-of-Truth Architecture

`docs/network.json` is the **single source of truth** for all device properties: IPs, MACs, serial numbers, hostnames, port assignments, firmware versions, and link topology. It uses the [NetJSON NetworkGraph](https://netjson.org) schema.

`scripts/sync-device-docs.py` reads `network.json` and overwrites specific sections in device markdown files and `README.md`. It is the only mechanism that should write to those sections.

## Workflow: Before and After Edits

**Before making changes**, run validation to surface any pre-existing issues:

```bash
python3 scripts/sync-device-docs.py --validate
```

**When editing `docs/network.json`**, ask before running the sync script — do not auto-run it. The workflow is:

```bash
# 1. Edit source of truth
$EDITOR docs/network.json

# 2. Ask user before running sync
python3 scripts/sync-device-docs.py

# 3. Commit together
git add docs/network.json docs/devices/ README.md && git commit
```

## What NOT to Edit Manually

These sections are **overwritten every time the sync script runs** — never edit them directly:

| Section | Marker |
|---------|--------|
| Device doc H1 title | First `# ` line — format `# TAG — Label` |
| Device info table | `<!-- NETJSON:START -->` … `<!-- NETJSON:END -->` |
| Interface/port table | `<!-- NETJSON:INTERFACES:START -->` … `<!-- NETJSON:INTERFACES:END -->` |
| README device registry | `<!-- NETJSON:REGISTRY:START -->` … `<!-- NETJSON:REGISTRY:END -->` |

To change device info, edit `network.json` and sync. To change narrative content in device docs (Role, Key Specs, Physical Connections, Protocol Map, Management Access, Notes sections), edit the markdown files directly.

## Device Naming Convention

Tags follow the pattern `{TYPE}-{N}` where type is 2–6 uppercase letters: `MOD` (modem/router), `NS` (network switch), `PC` (computer), `AP` (access point), `RTAC` (RTAC controller), `MET` (meter), `DEV` (development device). The pattern `[A-Z]{2,6}-\d+` is used to detect tag references; known non-tags like `RS-485`, `HDMI-1` are in the `KNOWN_NON_TAGS` exclusion list in the sync script.

## Lab Diagram

The `README.md` Lab Diagram is a **hand-authored Mermaid `graph LR`** block — it is not generated by `sync-device-docs.py`. When topology changes in `network.json` (new device, new cable, changed port), the Mermaid block must be updated manually to match.

Two authoring constraints to know:

- **Mermaid node IDs cannot contain hyphens.** Device tags like `MOD-1` become `MOD1`, `NS-2` becomes `NS2`, etc. as Mermaid node identifiers. The display label still uses the full tag: `MOD1["MOD-1\nModem / Router"]`.
- **Port labels go on edge labels**, not node labels. Format: `-->|"ETH - SRC:port -- DST:port"|` for Ethernet; omit the label entirely for cellular/WiFi.

The three `subgraph` blocks map directly to the three subsystems (DEV, EMA, TGT). When adding a device, add it to the correct subgraph and wire its edges following the connection type standard below.

The **Device Registry table** in `README.md` (below the diagram) *is* auto-generated — never edit it directly; run the sync script instead.

## Diagram Connection Type Standard

All topology diagrams in this repo use these Mermaid line styles — maintain this convention:

| Style | Medium | Port Labels |
|-------|--------|-------------|
| `A --> B` | Ethernet (physical copper) | Yes — `SRC:port -- DST:port` |
| `A ==> B` | Cellular / LTE / 5G | No |
| `A -.-> B` (no label) | WiFi | No |
| `A --o B` | RS-485 / Serial | Yes |
| `A -.-> B` (with label) | Planned / inactive link | Yes |

## Design Decisions

These were made deliberately — understand them before suggesting changes:

**`network.json` is the only writable source for device data.** IPs, MACs, serial numbers, ports, and link topology live there and nowhere else. The sync script propagates that data outward; device markdown files are consumers, not co-owners, of that information.

**NETJSON markers define a hard boundary in device docs.** Sections between the HTML comment markers are owned by the sync script. Sections outside them are owned by the human editor. Claude should only edit the human-owned sections directly; all machine-owned sections go through `network.json` + sync.

**Sync is prompt-before-run, not automatic.** After a `network.json` edit, Claude asks before running the sync script. This keeps the human in the loop on what files will change before they do.

**Validation runs before edits.** Running `--validate` first surfaces pre-existing issues so they aren't attributed to new changes.

**The Mermaid diagram and `network.json` topology are intentionally separate.** The diagram is a human-readable visual; `network.json` is the machine-readable record. Keeping them separate avoids generating Mermaid from JSON (lossy, fragile) while still having a single authoritative data source. The tradeoff is that diagram updates require a manual step when topology changes.
